## 1. 目标与范围

让 Codex 与 Cursor 在同一项目使用同一套规则；让不同项目复用通用约定，同时保持各自的需求、技术栈与发布流程独立。采用的规则必须随代码版本保存，能离线读取、核验来源、显式升级和回滚。

项目负责人已批准此方案及文档迁移。实施范围、已验证事项和待验证事项记录在实施计划中。

保障边界：文件与版本一致性可以机械检查；文档与代码语义、审批真实性和代理是否理解规则仍需评审和行为验收。不能用提示文件承诺模型每一步绝不偏离，也不能把一次验收当成永久保证。

## 2. 决策与备选方案

推荐 **共同入口 + 仓库内通用规范副本 + 项目适配 + 项目事实文档**。跨项目通过固定版本引入规范，升级通过可审查的变更完成。

| 方案 | 取舍 | 结论 |
| --- | --- | --- |
| Codex/Cursor 各写一套规则 | 入口原生，但正文重复且会漂移 | 不采用 |
| 只用个人全局规则或在线规则链接 | 本地省文件，但项目不可独立复现 | 不采用 |
| 两工具共用 AGENTS.md，所有细则堆在其中 | 加载直接，但项目增长后上下文和维护成本高 | 仅将其作为精简入口 |
| 通用规范随项目保存并固定来源版本 | 有物理副本，但项目可复现且升级可控 | 推荐 |
| Git submodule、实时远程加载、自动追随 latest | 引入部署或运行时依赖，当前收益不足 | 不采用 |

Codex 和 Cursor 均有 AGENTS.md 支持；Cursor 的文件引用不会自动内联目标全文。因此核心执行要求直接进入入口，详细规范通过明确阅读路由加载。[Codex 文档](https://learn.chatgpt.com/docs/agent-configuration/agents-md)、[Cursor 文档](https://cursor.com/docs/rules)。实际安装版本、全局覆盖和团队规则仍需分别验收；不依赖两工具有相同的隐藏优先级。

## 3. 四类职责及唯一维护位置

仓库采用以下结构。

```text
AGENTS.md                            两工具入口：简短执行要求和阅读路由
docs/
  governance/
    documentation.md                 通用文档分类、状态、批准、引用规则
    workflow.md                      通用任务分级、实施、验证与交付流程
    upstream.json                    来源、固定 revision、受管文件摘要
    project.json                     项目路径范围、入口及检查参数
  contributing.md                    本项目阅读路由、命令、环境和例外
  README.md                          实际文档导航
  prd/ rfcs/ design/ specs/ plans/    本项目需求、决策、实现依据和记录
  product/ assets/                   本项目发布材料及资源
scripts/governance/check.mjs          与通用规范同版本的检查器
.github/pull_request_template.md      项目交付证据模板
.github/workflows/ci.yml              项目检查与合并门禁
```

所有通用规范及适配数据均位于 docs/governance。规范是面向工具和人的普通文件，不是依靠文件夹名称自动触发的工具功能。

| 层次 | 权威内容 | 禁止混入 |
| --- | --- | --- |
| AGENTS.md | 必须读什么、先记录决定、不得代批、真实验证、完成时同步记录 | 完整状态表、具体测试命令、当前版本和进度 |
| 通用规范 | 可移植的规则正文、稳定条款 ID（如 DOC-APPROVAL、FLOW-VERIFY） | Chrome、SnapInsight、npm 或固定业务文件名 |
| 项目适配 | project.json 定义机器路径配置；contributing 定义人类执行说明和命令 | 通用规则全文或重复产品需求 |
| 项目事实 | PRD/RFC/设计/契约/进度、实际索引、历史证据 | 新的一套通用批准流程 |

project.json 只保存检查参数，不复制文档状态、审批记录、任务清单或测试命令。docs/README.md 只维护索引；contributing 用链接指向相关文档，不再维护另一份当前文档清单。

### 3.1 docs 分类的复用边界

通用 documentation.md 定义 discovery、rfcs、prd、design、specs、plans 的职责、英文文件命名、RFC/PRD 大写约定、状态和引用原则；项目按需启用类别，不强迫创建空目录。discovery 保留问题、选项、初步建议和理由的格式；重要决定进入 RFC，接口字段进入 specs。

SnapInsight 的适配声明实际采用的类别和 product/assets 用途；PRD-snapinsight.md 的名称、Prompt API 的边界、Chrome 商店流程都留在项目文档。项目 .venv 要求保留在 contributing 的条件性 Python 约束，不能作为所有项目的默认依赖。

### 3.2 读取流程

AGENTS.md 直接要求：开始实质项目工作前读本地通用规范、contributing 和索引；实施前再读当前进度、计划及受影响领域的依据。只读问答仅读所需材料，不制造任务或审批。相同会话不无故重读未变化文件；规则/相关依据发生变化或上下文丢失时重新加载适用部分。

入口的少量核心执行要求引用稳定条款 ID，属于启动约束；详细定义只维护在通用规范。入口约束和正文冲突必须修正，不靠“后读到的文件”解决。首版仅根级 AGENTS.md，不引入嵌套覆盖。

## 4. 约定、项目参数与例外

项目适配是为通用规范填入允许的参数，不享有任意覆盖权。例外必须记录条款 ID、原因、适用范围、授权证据和复核条件；由负责人明确授权，已有授权不重复申请。例外不能伪造测试或审批，也不能绕过工具更高层约束。

适配、通用规则、当前需求发生冲突时，先查适用的批准及替代记录。没有明确解决依据时记录问题，继续不依赖该决定的工作。个人全局偏好、团队指令等外部条件不属于本仓库能强制控制的范围；验收须报告会影响一致性的覆盖，不输出私人配置或敏感内容。

## 5. 跨项目采用和升级

### 5.1 共享来源与项目运行副本

共享规范仓库拟名 project-governance，包含 rules、templates、checks 和正反例 fixtures。rules 与 checks 一起发布；templates 只用于初始化和升级参考。目标仓库提交完整的规则及检查器副本，日常执行不联网，不执行远端脚本。

来源分两种：

- **local**：本项目内孵化，没有上游仓库；来源字段为 null，不能伪造版本。受管摘要用于发现意外修改，修改时由规则评审更新。
- **upstream**：采用共享仓库一个不可变完整 Git commit；可附人类可读 release 标签，但 commit 是实际身份。upstream.json 记录来源和每个受管文件的来源路径、目标路径、SHA-256。

摘要只能检测漂移，不能证明维护者身份或审批真实性。受管文件与摘要同时被修改仍需评审；采用时核对来源 commit 内容，CI 离线检查本地完整性。

### 5.2 首次采用

1. 选择来源版本，审阅通用规范、检查器和变更说明。
2. 把规范与检查器写入约定目标路径，记录来源；不覆盖已有项目文件。
3. 根据模板创建或合并 AGENTS.md、contributing、project.json 和 CI。存在冲突则展示差异，不静默覆盖。
4. 填入实际目录和验证命令，迁移原规则，修复现行文档基线。
5. 运行检查器和双工具加载/行为验收，评审后合入。

### 5.3 升级

显式选择新 commit；比较旧受管摘要、本地实际文件和上游新文件。若受管正文被本地修改，先解释偏离并把项目差异转为适配/授权例外，或明确采用一个新的上游分支版本，不能自动冲掉本地改动。

升级一次性更新通用规范、检查器和来源记录；项目配置按 schemaVersion 迁移。AGENTS.md、contributing、PR 模板和 CI 是项目拥有的文件，只比较新模板后合并必要变化，不整套覆盖。检查格式的破坏性变化必须给出迁移说明，未知 schemaVersion 直接报错。

规则正文变更优先回到共享来源；项目例外留在适配。每个项目可以停留在不同的固定版本；跨项目统一意味着共享来源和可追踪采用，不表示所有项目必须同时升级。

### 5.4 回滚与发布节奏

回滚完整采用/升级变更，包括规则、检查器、来源记录和必要的配置迁移；不能只退回规范而留下不兼容的检查器。升级前后均跑契约样例。远端分支设置如需回退，单独记录，Git 回滚不等于远端设置回滚。

第一阶段先在 SnapInsight 孵化完整分层及检查器，用一个不含 Chrome 的最小样例验证可移植性。第二个真实项目采用时再建立共享来源和提取提交；未创建上游前保持 local。先用审查后的复制和 diff 完成采用/升级，项目数量增加后才自动化同步；本设计不要求先开发通用安装器。

## 6. 文档生命周期与批准范围

按用途区分规范性文档（normative）和事实记录（record），再使用 Status 与 Applicability。具体字段及合法组合见配套 spec；Draft/current 的任务记录可以反映当前进度，但 Draft/proposed 的契约不能成为获批依据。

### 6.1 新文档与实质修订

- 新需求、架构或契约先形成提案；负责人确认后才能作为现行实施依据。每次确认记录真实证据及所覆盖的范围，不替用户审批。
- 已批准文档的实质修订必须引用覆盖本次变化的明确授权，或形成新的待审 amendment/RFC。原审批不自动授权新正文。
- 待审期间保留原现行文档，不用待审内容覆盖其权威正文；提案引用最后有效基线的 commit/path，获得授权后再在同一变更中更新现行正文、批准记录和变更记录。
- 编辑性修改不重复审批；记录为何不改变语义。已明确授权范围内的修改引用授权即可，不反复确认。
- 变更的实质性及批准覆盖范围由差异评审判断；检查器只核验字段、状态和证据结构，不能用字符差异假装识别语义。

批准证据包含确认人、日期、可追溯来源、批准范围和修订标识（如 PR/提交或本地评审快照摘要）。私有聊天只摘录必要确认内容，不强制把整个聊天公开。历史证据找不到时标记未核实；迁移时需要当前基线明确确认，不能追认历史审批已发生。

### 6.2 替代与历史

整份文档被替代时标记 Superseded/historical 并链接替代文件；部分变化更新现行正文及 Change Record，不废弃仍有效的要求。历史测试和发布记录保持当时事实。新日期不代表更高权威；替代必须明确范围和批准。

## 7. 工作流程与交付证据

| 任务 | 要求 | 不额外要求 |
| --- | --- | --- |
| 只读问答 | 读取适用材料，注明证据边界 | 新建任务、RFC 或审批 |
| 文案、文档整理 | 更新目标文件，检查结构和链接 | 产品测试或新 RFC |
| 已批准范围内修复 | 简短进度条目、文档影响说明、适用验证 | 每个 bug 都建独立计划 |
| 范围/架构/契约变化 | 必要的 discovery/RFC、设计/规范同步、范围明确的批准 | 重复申请已有授权 |
| 发布 | 采用本项目 release-process 与发布清单 | 再维护一套通用发布步骤 |

开始实施更新总进度；批次完成同步清单；交付说明真实命令、结果、适用版本和未验证项。“无文档影响”允许有理由的结论，由评审核验。格式检查、行为测试与语义评审分工；触碰文档文件并不等于完成文档同步。

SnapInsight 的具体 npm 命令、浏览器场景及 Python 环境约束写入 contributing；通用 workflow 仅要求执行项目配置的验证并如实记录。规则和检查器的修改必须显式说明影响，不能为让 CI 通过而悄悄降低要求。

## 8. 检查与合并约束

配套 [spec](../specs/project-governance-spec.md) 定义确定的文件集合、元数据、索引、来源格式及退出码，避免由实现者自行猜测。

- 本地默认检查工作树，只是预检；index 模式验证待提交快照；CI 用 commit 模式验证实际被测提交。报告必须注明模式和快照身份。
- 结构检查覆盖受管摘要、项目配置、入口、状态组合、索引、替代关系和本地引用。
- 审批范围、文档与代码一致、规则是否被不当放宽由评审核验。
- CI 使用稳定的 Project governance 名称，所有 PR 运行；现有扩展检查独立保留。不靠路径过滤跳过必需检查。
- main 的 required checks 与评审要求需在远端实际配置和核验；工作流 YAML 本身不构成分支保护。单人项目无法提供独立评审时如实记录降低的保障，不用机器人自审冒充。
- 检查器不能在普通验证时安装依赖、拉取远端、更新规则或修改工作树。

原约定基线固定为仓库 commit `2674a9b630dca079b07dab266451ae7d3afd97f7`，可以通过 `git show <commit>:<path>` 查看；当前工作树这些规则与基线一致后方可使用此映射，若已变化须重新记录实际迁移基线。

| 原路径（历史依据，不是迁移后的运行入口） | 新归属 |
| --- | --- |
| .cursor/rules/assistant-agreement.mdc | 通用 documentation/workflow；入口保留必要执行要求 |
| .cursor/rules/implementation-workflow.mdc | 通用闭环要求 + contributing 的实际阅读路由 |
| .cursor/rules/python-venv-workflow.mdc | contributing 的条件性 Python 环境要求 |

迁移逐项核对：讨论落盘、问题驱动 discovery、RFC 触发条件、审批归属、状态、命名、PRD 变更记录、Mermaid、开始/结束进度更新均保留。通用目录分类从 docs/README.md 迁到 documentation，README 转实际导航。

删除旧规则前扫描所有入站引用：当前指导改为新入口，历史依据改为不可变 commit/path，含本 RFC、审核记录和所有旧文档，不仅更新 README。旧文档的历史引用可以保留为明确的 Git 证据，不要求不存在的工作树链接仍能打开。

在同一候选迁移分支上完成规则迁移、文档基线修复和检查，通过双工具新会话验收后才切换主线。[RFC-009](RFC-009-governance-rollout-before-cursor-acceptance.md) 记录了仅适用于 SnapInsight PR #12 的一次例外。默认移除全部重复 .mdc；若已支持的 Cursor 版本实测需要兼容入口，可启用固定模板 project-entry.mdc，只要求读取根 AGENTS.md，配置必须明确标记此模式。兼容入口不能添加另一份规则正文。

## 10. 实施、验收与风险

详细步骤及反例见 [实施计划](../plans/shared-agent-governance-implementation-plan.md)。依次完成设计复核、现行文档确认、规则迁移、检查器、双工具验收、远端门禁核验；跨项目提取在第二项目出现时进行。

主要风险及边界：

- 全局覆盖或工具加载差异：用实际版本的新会话验证，失败不宣称一致。
- 通用规则过重：只读问答免流程，类别按需启用，入口精简；先两份通用文件。
- 规则副本漂移：受管清单和摘要检测，显式升级，适配不直接改共享正文。
- 审批形式化：只承认真实范围证据，语义由评审，不把元数据当批准本身。
- 迁移误删历史：固定基线并扫描入站引用，历史内容不批量改成新事实。
- 检查器引入工具依赖：首版需要 Node 24+ 和 Git，仅用于治理验证；这不要求其他项目应用本身采用 JavaScript。
